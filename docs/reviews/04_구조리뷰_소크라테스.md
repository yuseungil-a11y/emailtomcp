# EmailToMCP DESIGN.md v0.1 구조/유지보수성 리뷰 (Socrates / code-reviewer)

## 1. 모듈 경계와 의존 방향 (높음)

### 1.1 mcp_server ↔ autoreply 순환 의존
- 잡 토큰을 발급하려면 autoreply가 mcp_server를 호출하고, `submit_auto_reply` 처리 결과를 반영하려면 mcp_server가 autoreply를 호출한다. 두 패키지가 서로를 참조하는 순환이다.
- **수정**: `core/events.py`에 "job_submitted" 이벤트를 발행하고 autoreply가 이를 구독하게 한다.

### 1.2 서비스가 runtime/qt_bridge를 직접 import하지 않는다
- 서비스는 `core.events`로만 이벤트를 발행한다.
- `qt_bridge`는 그 이벤트를 구독해 Qt Signal로 다시 내보내는 어댑터 역할만 맡는다.
- 원칙을 한 줄로 명시한다: "services는 core만 알고 runtime은 모른다."

### 1.3 레이어 재정의
- `mcp_server`는 ui와 같은 두 번째 진입점(front door)이다.
- `backend.py`는 루프를 띄우고 이미 조립된 서비스를 실행하는 인프라 역할만 한다.
- 의존성 주입(와이어링)은 `app.py`에서 처리한다.

### 1.4 초안 생성 로직이 세 곳에 중복될 위험
- 초안은 UI 작성창, MCP `create_draft`, ReplyPolicy 세 곳에서 만들어진다.
- `mail/draft_service.py`를 추가하고 다음 공통 로직을 모은다: Re: 정규화, 주소 검증, 첨부 메타 처리.

## 3. 스레드 모델 (높음)

방향(Qt와 별도로 asyncio 스레드 1개, qasync 미사용)은 적절하다. 다만 아래 사항을 보완해야 한다.

### 3.1 `to_thread`와 thread-local 연결이 맞지 않는다
- `to_thread`는 기본 executor의 워커(최대 32개)를 쓰므로 SQLite 연결이 난립하고 busy 경합이 생긴다.
- **수정**
  - 크기를 제한한 전용 executor(max_workers=4)를 만들고 `run_in_executor`로 호출한다.
  - DB 쓰기는 **단일 writer**(큐로 직렬화)로 모은다.

### 3.2 상태 전이 경쟁
- 재시작 시 running을 queued로 복구하는 로직과 runner가 done을 쓰는 로직이 경쟁할 수 있다.
- **수정**
  - 모든 전이를 `UPDATE ... SET status=? WHERE id=? AND status IN (...)` 형태로 하고 rowcount로 성공 여부를 확인한다.
  - 이를 `Repository.transition(id, from_states, to_state)` 단일 함수로 구현한다.
  - messages, drafts, jobs의 상태 컬럼 모두에 같은 방식을 적용한다.

### 3.3 `run_coroutine_threadsafe` 오류 처리 보일러플레이트
- `qt_bridge.call_backend(coro, timeout)` 헬퍼에서 예외를 받아 Signal로 다시 내보내는 처리를 한 곳에 모은다.

### 3.4 종료 순서 명문화 (P0)
다음 순서로 종료한다.
1. 새 잡 수락을 중단한다.
2. 실행 중인 잡을 취소하거나 끝날 때까지 기다린다.
3. uvicorn을 shutdown한다.
4. 이벤트 루프를 stop한다.
5. 스레드를 join한다.
6. 락을 해제한다.

### 3.5 대안
MCP SDK가 asyncio를 요구하므로 asyncio 사용은 피할 수 없다. 현재 안을 유지하고 단일 writer 원칙만 추가한다.

## 4. DB 스키마

### 4.1 `messages.auto_reply_status`에 CHECK 제약이 없다
다른 상태 컬럼과 맞춰 추가한다.
```sql
CHECK (auto_reply_status IS NULL OR auto_reply_status IN (...))
```

### 4.2 같은 상태를 세 곳에서 기록한다
- 자동회신 상태가 messages.auto_reply_status, jobs.status, log.outcome에 따로 기록된다.
- **수정**
  - jobs를 단일 진실 소스로 삼는다.
  - messages 쪽은 같은 트랜잭션 안에서 함께 갱신하거나 뷰(view)로 대체한다.

### 4.3 send_log는 MVP에서 뺀다
레이트리밋은 drafts와 messages(sent)를 조회해서 계산한다.

### 4.4 FTS에 JSON 배열 문자열을 넣지 않는다
주소 필드는 쉼표로 이은 평문 주소를 색인한다.

### 4.5 인덱스 추가
- `attachments(message_id)`
- `auto_reply_jobs(status, next_run_at)`
- `mcp_audit(ts)`

### 4.6 마이그레이션 러너 구체화
- `migrations/0001_init.py`처럼 파일마다 `upgrade(conn)`을 두고, `user_version`으로 순차 적용한다. 각 마이그레이션은 하나의 트랜잭션으로 실행한다.
- SQLite는 CHECK나 NOT NULL을 ALTER로 바꿀 수 없다. 그래서 테이블 재생성 헬퍼(`_rebuild_table.py`)를 P0에서 미리 만든다.

### 4.7 JSON 컬럼
현재 사용은 적절하다. 다만 `settings.value_json`은 pydantic으로 검증한다.

## 5. 오류 처리, 로깅, 설정 (저설계, 높음)

1. **예외 계층**: `core/errors.py`에 `EmailToMcpError`를 두고, 그 아래 `TransientError`, `PermanentError`, `AuthError`를 둔다.
2. **로깅**
   - stdlib logging만 쓴다.
   - logger 이름은 패키지 경로를 따른다(`emailtomcp.mail.sync` 등).
   - RotatingFileHandler 하나를 `app.py`에서 한 번만 설정한다.
   - 자동회신과 발송 경로의 로그에는 `job_id`/`message_id`를 반드시 남긴다.
3. **설정**: 모든 설정은 DB의 `settings` 테이블 하나로 모은다. `config/paths.py`는 경로 계산만 맡는다.
4. **계정 격리**: SyncService는 계정 단위로 try/except를 둔다. 한 계정이 실패해도 다른 계정 폴링은 계속돼야 한다.

## 6. GitHub 자동 업데이트와 버전 0.0.0

### 6.1 위치
`src/emailtomcp/update/`를 runtime과 같은 수준의 인프라 패키지로 둔다.

| 파일 | 역할 |
|---|---|
| `checker.py` | 업데이트 확인 |
| `verify.py` | 검증 |
| `installer.py` | 설치 |

- update는 core와 config만 알고, mail, rules, autoreply는 모른다.
- 호출 경로는 두 가지다: UI 메뉴에서 수동 확인, backend 주기 스케줄러가 이벤트로 알림.

### 6.2 단일 버전 소스
- 버전은 `src/emailtomcp/_version.py`의 `__version__ = "0.0.0"` 하나로 관리한다.
- pyproject는 `dynamic = ["version"]`과 `[tool.setuptools.dynamic] version = {attr = "emailtomcp._version.__version__"}`로 이 값을 읽는다.
- 1인 MVP에서는 **수동 bump**를 권장한다. setuptools-scm을 쓰면 커밋마다 `0.0.0.dev3+g…`처럼 버전이 붙어 "0.0.0 시작"과 헷갈린다.

### 6.3 브랜치와 태그
- 브랜치는 `main`, 릴리스 태그는 `vX.Y.Z` 형식으로 한다.
- draft와 pre-release는 기본적으로 제외한다.
- 태그와 릴리스는 CI(테스트 → 빌드 → 게시)를 통과한 뒤에만 만든다.

### 6.4 범위 조정 권고 (가장 중요)
- **Windows**: onedir 구조에서는 자기 자신을 교체할 수 없다. 헬퍼 프로세스가 다운로드, SHA256 검증, 스테이징, 종료 대기, 교체, 재실행을 차례로 맡아야 한다.
- **macOS**: 번들 전체를 교체해야 하고 quarantine 처리도 필요하다.
- 이 작업량이 상당하다. 그래서 **v0.1~0.2에서는 "새 릴리스 확인 + 알림 + 릴리스 페이지 링크"까지만** 구현하고, 무인 설치는 P1~P3가 안정된 뒤 후속 버전에서 하기를 권장한다.
