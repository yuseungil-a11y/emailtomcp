# 데카르트 최종 재확인: EmailToMCP 자동 업데이트 (M-1 / M-2 / C2 / L-8 / C4)

## 판정
- **이번 수정 범위(M-1, M-2, C2, L-8, C4)는 Go입니다.** 주장한 수정이 모두 코드와 문서에 실제로 들어가 있습니다. 테스트 기대값도 새 분류에 맞게 바뀌었고 재실행해서 통과를 확인했습니다.
- **v1.0.0 출시는 여전히 No-Go입니다.** `EMBEDDED_PUBLIC_KEYS = ()`가 그대로입니다(keys.py:58). H-1(C1, 운영 키 내장)은 출시게이트 테스트만 추가됐고 키 자체는 아직 없습니다.
- M-1 분류 경계는 정확합니다. 다만 경계 안쪽에 실제 운영에서 생길 수 있는 오탐 시나리오가 하나 남아 있습니다("발견 사항" 1번). 출시 차단 사유는 아니고 권고입니다.

## 항목별 확인

### M-1: 분류 경계 (가장 중요, 정확함)
`src/emailtomcp/update/keys.py`의 `verify_minisign`(172~205행) 확인:

| 경우 | 결과 | 위치 |
|---|---|---|
| 신뢰 키 목록이 빔 | `SignatureUnverifiable` | 183~184행 |
| UTF-8 오류, 4줄 아님, 접두사 오류, trusted comment 1KB 초과, base64/길이/알고리즘 오류 | `SignatureUnverifiable` | `parse_signature` 134~169행 |
| 내장되지 않은 key_id | `UnknownSigningKey`(하위) | 186~188행 |
| key_id 일치, 본 서명 검증 실패 | `SecurityError` | 195~198행 |
| key_id 일치, global signature 검증 실패 | `SecurityError` | 199~204행 |

- `verifier.py` 149~152행은 `SignatureUnverifiable`만 잡아 `ManifestRejected(2)`로 바꿈. `SecurityError`는 그대로 올라감.
- 해시 충돌([9])은 `SecurityError` 유지.
- 경보는 "key_id 일치+Ed25519 실패"와 "해시 충돌" 두 경우뿐. 너무 넓지도 좁지도 않음.
- 위조 쪽 구멍 없음: 미내장 key_id는 경보만 안 날 뿐 검증은 실패, 상태도 저장 안 함. key_id 사칭 위조 서명은 여전히 경보.
- `checker.py` 281~286행: `UnknownSigningKey` 원인이면 "새 서명키를 모릅니다 — 수동 업데이트 필요" 별도 표시, halted 안 됨.
- `parse_public_key`(내장 키 자체 형식 오류)는 여전히 `SecurityError` — 빌드 구성 오류 반응이라 적절.
