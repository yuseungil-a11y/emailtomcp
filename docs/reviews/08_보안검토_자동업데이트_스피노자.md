# EmailToMCP 자동 업데이트(update/) 구현 보안 검토: C1 이행 확인 (Spinoza)

코드를 읽어 검토했습니다(Read/Grep). 실행은 두 가지만 했습니다. URL 검증 함수 단독 호출(17개 입력)과 httpx2 디코더 소스 확인입니다. pytest 스위트는 돌리지 않았습니다.

**종합**: C1의 핵심 요구는 코드로 충족됐습니다. Critical은 없습니다.
- 서명을 먼저 검증하고 파싱은 그다음입니다(verify-then-parse).
- minisign은 본 서명과 global signature를 둘 다 검증합니다.
- 롤백·다운그레이드·같은 버전 다른 해시를 막습니다.
- 크기 상한이 HTTP 클라이언트와 검증기 양쪽에 있습니다.

다만 v1.0.0 출시를 막는 문제가 1건 있고, 경보 분류에 운영상 위험이 있습니다.

## 질문별 판정

**1. 운영 공개키를 비워 둔 판단과 fail-closed 동작: 판단은 옳고, 우회할 틈은 없습니다.**
- 테스트 키는 공개된 시드에서 결정적으로 만들어집니다(`tests/fakes/fake_github_releases.py:44-49`). 이 키를 운영 빌드에 넣으면 누구나 매니페스트를 위조할 수 있습니다. Edison의 거부가 맞습니다.
- 키가 비면 두 겹으로 닫힙니다: `checker.py:251-255`(네트워크 요청 전 "확인 불가"), `keys.py:159-160`(키 목록 비면 SecurityError).
- 키를 바꿔 넣는 경로는 생성자 인자(`trusted_keys`)뿐이고 테스트 2곳만 씁니다. `app.py:867`은 넘기지 않습니다. 환경변수·설정·DB 경로 없음.
- 가드 테스트 `test_update_keys.py:103-110`가 테스트 키의 운영 상수 유입을 막습니다.
- 다만 키가 빈 채로 출시하면 이 판단이 그대로 출시 차단 문제가 됩니다(H-1).

**2. 11단계 순서: 설계대로입니다.**
- `verifier.py:133-142` 순서: 크기 확인 → 서명 검증 → `parse_manifest`(:146). 서명 전에 본문을 해석하는 코드는 없습니다.
- [5]→[11] 순서도 맞습니다. 만료([7])는 롤백 검사([6]) 뒤라 "만료된 옛 매니페스트"도 먼저 롤백으로 걸립니다.

**3. 같은 버전 다른 해시, 롤백, 다운그레이드: 막힙니다.**
- 같은 버전 다른 해시: `verifier.py:185-194`에서 slot 단위 비교 후 SecurityError. 충돌 상태는 저장 안 함.
- 롤백: `:169-171`에서 `issued_at < last_issued_at`이면 거부.
- 다운그레이드: `:212-218`과 `version.py` 모두 `packaging.version.Version` 비교. 문자열 비교 없음. stable 채널의 rc도 거부.

**4. URL 접두사 우회: 막힙니다.**
- `../`, `%2e%2e`, `x@evil.com`, `github.com@evil.com`, `?q`, `#f`, `..`, `./`, 역슬래시, `:443`, 대문자 스킴, 탭 — 모두 False.
- 방어 구조(`manifest.py:58-81`): 접두사 + 금지문자 + `urlsplit` netloc 정확히 github.com + `.`/`..` 경로 조각 금지.
- 같은 검사를 `checker.py:110`, `app.py:741`, `update_banner.py:46-65`에서 세 번 더 함.
- 남는 틈은 L-3(비ASCII 허용)뿐, 호스트를 벗어나지는 못함.

**5. minisign 파서(`keys.py`): 정확합니다.**
- 서명 파일 정확히 4줄, 접두사 확인, base64 strict, 길이(74/64바이트) 엄격 확인.
- `ED`/`Ed` 둘만 허용, key_id로 키 탐색.
- global signature를 `signature(64B) || trusted_comment`로 검증(:175-180, minisign 원 사양과 동일).
- trusted comment와 JSON 값 대조(`verifier.py:88-113`)는 app/channel/version/issued 4개 전부 확인. 중복 키, `=` 없는 토큰, 시간대 없는 issued는 거부.

**6. 64KB 상한 양쪽 적용: 됩니다.**
- 클라이언트(`release_client.py:119-129`)는 Content-Length 선확인 + 스트리밍 누적 바이트 확인.
- 검증기(`verifier.py:134-137`)도 다시 확인(주입된 HttpClient가 상한을 안 지켜도 막힘).
- 압축 폭탄은 httpx2 디코더의 `max_length` 단위 절단으로 완화.
- 남은 문제: 전체 시간 상한 없음(M-2).

**7. 설정과 상태 저장: 새로 생긴 명백한 취약점은 없습니다.**
- 신뢰 상태는 검증 통과 후에만 저장(`verifier.py:202`). 읽을 때 방어적 정리(`state.py:62-80, 113-122`).
- DB 변조(T3)는 방어 대상 밖 전제 수용.

**8. 경보 뒤 "수동 확인 허용, 성공하면 재개": 적절합니다.**
- 해제(`checker.py:307`)는 11단계를 전부 통과해야만 일어남 — 공격자가 정지를 풀 수 없음.
- 동결 공격은 7일 경과 배너로 재알림.
- 다만 정지 조건이 너무 넓음(M-1), 해제 시 경보 기록이 덮어써짐(L-9).

## 지적 목록

### Critical
없음.

### High

**H-1. 운영 키 없이 v1.0.0을 출시하면 그 설치본은 영구히 업데이트 알림을 못 받습니다(출시 차단).**
- 위치: `keys.py:48`, `checker.py:251-255`.
- 공개키는 원격으로 추가할 수 없어, 키가 빈 1.0.0 사용자는 수동 재설치 말고는 방법이 없습니다. 사용자에게 알려지지도 않습니다(`is_stale`이 항상 False).
- 수정 권고: ① §14.7 절차로 K1/K2 오프라인 생성·내장 ② 정식(비dev) 빌드에 키가 없으면 실패하는 출시 게이트 테스트 추가(`test_update_keys.py:113-117`은 지금 키가 있을 때만 검사) ③ release 워크플로(아직 없음)에 이 게이트 포함.

### Medium

**M-1. 형식 오류와 미내장 키까지 SecurityError로 분류해 오탐 경보·자동확인 정지가 납니다.**
- 위치: `keys.py:86, 116-142, 163-164`, `checker.py:274-276`.
- 시나리오: 사내 SSL 검사 장비가 차단 HTML을 200으로 돌려주면 파싱 실패 → 경보 → 정지. 키 회전(§14.7-6) 후 구버전 클라이언트도 매 회전마다 대량 오경보.
- 수정 권고: 경보·정지는 "내장 키의 암호학적 검증 실패"와 "[9] 해시 충돌" 두 경우로만 좁힌다. 형식 오류·미내장 key_id는 "확인 불가"로 낮춘다. **1.0.0부터 들어가야** 이후 키 회전 때 오경보가 안 남.

**M-2. 다운로드에 전체 시간 상한이 없어 느린 응답이 작업 스레드와 앱 종료를 붙잡습니다.**
- 위치: `release_client.py:104-129`, `runtime/backend.py:72, 154`.
- httpx timeout이 읽기 1회당 10초뿐이라, 9초마다 1바이트씩 보내는 서버면 64KB 받는 데 며칠 걸림. 그동안 `Backend.stop()`의 `executor.shutdown(wait=True)`가 앱 종료를 무기한 지연.
- 수정 권고: 스트리밍 루프에 벽시계 기준 전체 상한(요청당 30초) 추가, 넘으면 TransientError. 서명 파일 상한은 별도로 1~2KB로 낮춘다(64KB는 과함).

### Low
- **L-1**: 한 번도 성공한 적 없으면 7일 경과 경고가 영원히 안 뜸(`checker.py:199-202`) — "첫 확인 시도 시각"을 별도 저장 권고.
- **L-2**: `save_trust`가 트랜잭션 3개로 나뉨(`state.py:124-133`) — 단일 writer 트랜잭션 권고.
- **L-3**: URL에 비ASCII, `;`, `//` 허용(`manifest.py:52`) — 실제 위험은 낮으나 화이트리스트 권고.
- **L-4**: 산출물 `size` 최솟값 0(`manifest.py:94`) — U2 착수 시 `ge=1`로.
- **L-5**: 레거시 `Ed`(prehash 없음) 서명 허용(`keys.py:138`) — `ED`만 허용해 공격면 축소 가능(판단 사항).
- **L-6**: httpx를 직접 의존성으로 선언 안 함(mcp가 끌어온 httpx2 2.13.1에 의존) — mcp가 바뀌면 업데이트 확인이 조용히 영구 "확인 불가"가 됨. 직접 의존성 고정 + 해시 lock 권고.
- **L-7**: 툴팁/배너 QLabel이 자동 텍스트 형식(`main_window.py:1003`, `update_banner.py:267`) — 현재 실제 주입 경로는 없음, PlainText 명시 권고(방어 심층화).
- **L-8**: 범용 `UiApi.set_setting`으로 `update.*` 신뢰 상태 키도 쓸 수 있음(`app.py:733`) — 지금은 호출자가 고정 키뿐이라 안전하나, 나중에 노출되면 `update.last_issued_at`을 미래로 써서 영구 동결 가능 — `update.` 접두사 키 거부 권고.
- **L-9**: 경보 이력이 안 남고, `check_once`의 `last_status()`가 try 밖이라 DB 손상 시 예외-무누출 계약이 깨짐(`checker.py:225, 307`) — SecurityAlert 이력 누적 권고.
- **L-10**: `keys.py:8` docstring 경로가 실제(`tests/fakes/fake_github_releases.py`)와 다름.

## v1.0.0 릴리스 전 반드시 고칠 것
1. **H-1**: 운영 키 K1/K2 내장 + 정식 빌드 키 누락 시 실패하는 출시 게이트.
2. **M-1**: 경보 대상을 "암호학적 검증 실패"와 "해시 충돌"로 좁힌다. **1.0.0부터** 반영해야 이후 키 회전이 안전함.
3. **M-2**: 다운로드 전체 시간 상한 + 서명 파일 상한 축소.
4. 권장(작업량 작음): L-1, L-6, L-8.

## 운영 키를 넣은 뒤 다시 확인할 것
1. 실제 minisign CLI(`minisign -S`)로 만든 서명이 `verify_minisign`을 통과하는지 실물 상호운용 테스트(지금은 자체 fake 서명기만 사용). trusted comment 형식도 확인.
2. 예비 키(K2) 서명 매니페스트 수락 여부(§14.6 #20 실물판).
3. `key_id_hex` 표시가 `minisign -V`와 일치하는지(위키·README 게시 지문의 정확성).
4. 테스트 키 미유입 가드가 운영 키 상태에서도 통과하는지.
5. 첫 운영 매니페스트를 GitHub Pages에 배포한 뒤: 리다이렉트/Content-Length 동작, 사내 SSL 검사 환경에서 M-1 수정 후 "확인 불가"로만 떨어지는지, 30일 재서명 일정 등록 여부.
6. 회전 리허설: K2로 서명+K3 내장 릴리스 후 구버전 클라이언트(K1/K2만 앎) 동작 확인(M-1 수정 결과 검증).
