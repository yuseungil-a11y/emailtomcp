# 릴리스 자동화 파이프라인 보안검토 — Spinoza

## 결론
- **v1.0.0rc1 같은 rc 시험태그로 파이프라인 돌리는 것: 조건부 Go.** rc태그는 후보매니페스트 안만듦(서명·Pages반영없이 draft/prerelease까지만). 조건2가지: `v*`태그보호 ruleset 실제설정, `persist-credentials:false` 반영권장.
- **첫 stable 릴리스 서명+Pages게시: No-Go.** H-1,H-2 선결필요. M-2~M-4는코드몇줄수준이라함께반영강력권고.
- Critical없음. 비밀키-CI분리는실제로완전함(CI에서명단계없음, Secrets참조0건, 외부인/포크트리거경로없음).
- `test_release_scripts.py` 37 passed.

## 확인된 양호사항
1. **트리거·토큰**: 트리거는 `push:tags:v*`하나뿐(pull_request_target/workflow_run/workflow_dispatch없음). 포크/외부PR은 upstream에태그push불가. 최상위permissions:contents:read, 쓰기권한은draft-release job에만. 스크립트인젝션없음(github.ref_name은env거쳐전달). 캐시미사용. Actions SHA 5개 git ls-remote로직접대조, 전부태그일치(checkout v7.0.1, setup-python v7.0.0, upload/download-artifact, attest-build-provenance).
2. **sign_release.py 비밀취급**: minisign호출은인자리스트+shell미사용, 암호관련인자없음, stdin/stdout/stderr가로채지않음, 예외메시지에키경로없음, 저장소안위치검사는resolve()+is_relative_to(심볼릭링크·정션추적, Windows대소문자무시비교, 범위한계는L-2).
3. **서명후자체재검증**: 실질적으로동작(key_id다르면UnknownSigningKey, 같은데키다르면SecurityError, 둘다ReleaseError로변환, trusted comment일치+앱의verify_manifest전체단계통과필요). 실패시임시파일삭제+기존결과보존(테스트확인됨).
4. **재서명내용불변비교**: issued_at/expires제외 최상위dict전체깊은비교(빠진필드없음). pydantic과json의중복키처리(마지막값우선)동일확인.
6. **build_manifest.py**: URL고정접두사+validator(scheme/host/path/../%/@재검사), platform/arch/kind슬롯중복 스키마강제, 파일명중복·64KB상한·CR포함·floor>latest·stable채널rc 전부거부.

## High

**H-1. 릴리스빌드의존성에 해시고정없음(§15.4·§15.5설계위반)**
- build job: `pip install -e ".[release]"`. draft-release job: `pip install --no-deps -e .`(hatchling/hatch-vcs가 고정없이PyPI에서받아짐), `pip install "pydantic>=2.7" "packaging>=24" "cryptography>=42"`. `dotnet tool install vpk`: 버전만고정, 해시미검증.
- 왜문제: 태그시점 PyPI에서풀린버전이 그대로배포바이너리에들어가고, 메인테이너는그결과물sha256에서명 — 공급망오염이서명으로정당화됨.
- 수정: 잠금파일(requirements-release.txt, pip-compile --generate-hashes 또는uv lock)+`pip install --require-hashes --no-deps -r ...`. hatchling/hatch-vcs도해시고정후 `pip install --no-deps --no-build-isolation -e .`. release.yml에 pip-audit단계추가.

**H-2. 서명직전독립검증없음(검증고리가순환구조)**
- sign_release는후보·산출물이서로맞는지만확인, 둘다같은draft에서내려받음 — draft수정권한자(쓰기권한자/탈취계정)나 contents:write토큰가진다른워크플로, 오염된draft-release job 중하나만있으면서로맞는악성쌍생성가능, 메인테이너가그것에서명.
- README 4단계의 gh attestation verify는"(선택)"으로만적혀있음.
- 수정: sign_release.py가서명전 `gh attestation verify <file> --repo ... --signer-workflow ... --source-ref refs/tags/v<ver>` 필수실행. `--expect-version`(필수)추가. 확인화면에 notes_summary/released_at/산출물URL표시. provenance는draft-release가아니라build job안에서생성.

## Medium

**M-1. draft-release job에 쓰기토큰과서드파티코드가함께있음**
- contents:write로 draft publish/릴리스편집/태그생성/보호안된브랜치(main,gh-pages등)push가능(같은저장소한정). checkout 기본값(persist-credentials:true)때문에토큰이.git/config에남아 이후pip설치패키지가읽을수있고 id-token:write(OIDC)도쓸수있음.
- 수정: ①후보생성·SHA256SUMS는read-only job서만들어artifact로전달, 쓰기job은checkout·pip없이gh release create만 ②모든checkout에persist-credentials:false ③쓰기job에GitHub Environment(release,승인자지정)적용(§14.7-4-4 Environments승인게이트구현) ④main·Pages소스브랜치보호+GITHUB_TOKEN이보호우회못하게설정 ⑤태그ruleset실제설정(태그push가능하면워크플로내용임의변경가능).

**M-2. 재서명기준점이"유효한서명"일뿐"최신게시본"아님(replay→동결공격연장)**
- 현재Pages파일기준점은변조본차단엔유효하나, **예전정상서명된구버전stable.json**을Pages소스에되돌리면검증통과 — 만료여부·버전미확인. 결과: 구버전에새30일유효기간부여, 신규사용자에게구버전이최신으로보임, 보안릴리스알림막힘, 낮은floor재활성.
- 수정: `--expect-version`필수+gh release list최근비-rc태그와기존매니페스트버전동일해야재서명. 기존expires이미지났으면경고후중단.

**M-3. 로컬PC시계를그대로신뢰**
- 재서명모드는하한(now>기존issued_at)만확인, 신규서명모드는시계검사아예없음, 자체재검증도같은잘못된now사용해못잡음. 시계빠른경우→추후정상서명매니페스트전부롤백거부(업데이트채널동결). 시계느린경우(신규서명)→게시본보다과거시각돼클라이언트전원롤백거부.
- 수정: github.com/Pages HTTPS Date헤더나NTP와비교해몇분넘게어긋나면중단. 신규서명모드도현재게시된stable.json(검증후)입력받아 now>issued_at과 새버전>=기존버전강제.

**M-4. 신뢰기준공개키를작업트리의keys.py에서가져옴**
- embedded_trusted_keys()가체크아웃된소스그대로읽음 — 악성커밋이EMBEDDED_PUBLIC_KEYS에공격자키추가+Pages에공격자서명stable.json두면 재서명사전검증통과, 메인테이너가공격자내용에K1으로재서명하게됨.
- 수정: 스크립트안에 K1 key_id `205BD649DF53346C`(또는공개키문자열) 별도고정, 내장키목록이정확히이값과일치할때만진행.

## Low

- **L-2**: 키위치검사범위좁음(이스크립트있는저장소만검사, 다른clone/Pages소스체크아웃/상위폴더git트리는못잡음, .gitignore에*.key패턴없음). 수정: 키경로상위폴더에.git하나라도있으면거부+.gitignore에*.key추가.
- **L-3**: 스키마가platform-kind조합강제안함(조합검사는build_manifest에만있어 손으로고친후보는서명단계통과). prepare_from_candidate가최종본에verify_artifacts재실행안함(현재는중복키처리동일해문제없으나방어차원재실행권장).
- **L-4**: 같은태그재실행시--clobber로draft자산교체됨(메인테이너가이미내려받은자산과달라질수있음, 클라이언트는해시불일치로fail-closed라위험낮으나혼란). 수정: 기존draft있으면실패시키고사람이지운뒤재실행.
- **L-5**(기존ci.yml, 범위밖): permissions없어저장소기본토큰권한따름, actions가SHA아닌태그로지정. 수정: permissions:contents:read명시+SHA고정.

## Velopack 훅 판단
`set_auto_apply_on_startup(False)`는§14.2("신뢰판단은서명매니페스트가전담")와일치. Velopack은UpdateManager로직접요청안하면스스로패키지안받는것으로알려짐(현재앱엔UpdateManager코드없어 자체업데이트적용경로안보임). **단실제Velopack빌드로검증필요**(이PC에velopack패키지없어 ①velopack==1.2.161 PyPI실존여부 ②App.set_auto_apply_on_startup메서드존재여부(없으면frozen앱이매번기동시AttributeError종료,CI --version스모크가잡아낼수있음) ③Velopack미설치onedir서run()호출시예외여부 미확인). 보안등급Low, 실제빌드검증필요.
