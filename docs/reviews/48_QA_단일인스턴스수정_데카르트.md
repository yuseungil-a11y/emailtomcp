## 결론: 조건부Go
이번수정으로생긴크래시·보안회귀없음(지정테스트16건통과, HMAC핸드셰이크불변). 단 **사용자별파이프이름이의도대로안됨(M-1)+이수정으로생긴새로운MCP연결실패경로(M-2)** 있음 — 출시전한줄수준보완권장(안하면"한글계정명은사용자구분안됨"을알려진이슈로등록하고출시).

**사용자가본"두프로세스동시생존"은데카르트도재현못함.** 실제원인일가능성높은다른경로하나발견(5항).

## 항목별결과

**1. try_acquire(app.py:1656-1704): 적합**. listen()반환값실제확인, 실패시errorString+키를경고로그+_server=None정리후True반환(기동안막음). 판단타당(단일인스턴스판정은실제QLockFile.tryLock(100)이함-문서와코드일치, listen실패로기동막으면다른계정이파이프이름선점만으로DoS가됨, 실패상태서도stdio프록시는가짜서버에토큰안보냄/HMAC검증). 권고(Low): 지금은로그에만남아사용자가못알아챔 — "활성화·MCP stdio연결불가"상태를상태바등으로표시권장.

**2. SINGLE_INSTANCE_KEY(local_handshake.py:46-65): 결함있음**
getpass.getuser()섞는것자체는맞으나 직접실행결과:
| 계정명/환경 | 생성된키 |
|---|---|
| UT | EmailToMCP-single-instance-UT |
| 유승일,홍길동 | 둘다 공용이름폴백 |
| kim철수,kim영희 | 둘다 EmailToMCP-single-instance-kim(충돌) |
| USERNAME등환경변수없음 | 공용이름폴백 |

폴백의보안영향없음(사용자명은원래추측가능값이라이름구분은보안경계아님, 실제방어선은DACL+HMAC, 폴백해도보안안약해짐).

- **M-1(Medium)**: 한글문자를_로바꾼뒤strip해서 한글계정명은전부공용이름폴백또는서로충돌 — 한국사용자환경서L-1의"사용자별구분"목적미달성(수정전과같은수준, 악화아님).
- **M-2(Medium, 이번수정으로생긴회귀)**: getpass.getuser()는Windows서환경변수만읽음 — GUI와stdio프록시의환경변수가다르면키가달라져프록시가앱을못찾음. 실측: 정상환경서는접속됨(테스트용가짜비밀값이라HMAC거부지만연결자체는됨). USERNAME등제거환경서는AppNotRunningError. Claude Desktop·Code가축소된환경변수로프록시띄우면MCP끊길수있음(수정전엔고정이름이라이문제없었음).
- **권장수정(M-1,M-2공통)**: 환경변수대신OS API로계정획득(Windows는GetUserNameW/os.getlogin(), 가능하면SID). 원문을sha256(...).hexdigest()[:16]같은해시로바꿔키에넣기. 한글계정명·환경변수없음·폴백경로단위테스트현재없어함께추가필요.

**3. activate신호유실수정(processEvents펌핑): 무해하나효과미입증**
별도하네스로진쪽프로세스15회씩실행해activate수신횟수측정 — 수정전빌드exe15/15수신, 수정후dev코드15/15수신. **즉수정전코드에서도유실이재현안됨.** waitForBytesWritten이False반환하는건Windows파이프에서이미커널버퍼로쓰기끝나대기할바이트없을때도생김 — Edison이이를실패신호로오해했을가능성. 수정이하는일: processEvents()는블로킹아니라유실을보장해서막지못함, 실제보장역할은추가된waitForDisconnected(200)(200ms상한). 여전히남은유실경로(Low,UX문제): (a)이긴쪽tryLock성공했지만아직listen전수ms사이두번째실행 (b)이긴쪽기동중이벤트루프막혀있을때(DB마이그레이션,MCP시작최대15초)연속두번째이후접속이PIPE_BUSY걸리고waitForConnected(200)타임아웃 (c)listen실패한인스턴스 — 세경우모두진쪽은조용히종료, 기존창비활성화, 프로세스2개남지는않음.

**4. 지정테스트재현: 16 passed(5.69s)**. 대상5파일. 문서불일치(Low): test_single_instance_guard.py docstring에"PID2개동시생존버그재현됐다"고적혀있는데Edison보고"재현못함"과모순 — 사실대로수정필요.

**5. "두프로세스동시생존"재현시도: 재현안됨**
전제: dist exe는21:47빌드로소스수정(22:19)보다앞섬(수정전코드로시험). 시나리오6종(즉시연속2개×offscreen/GUI, 4개동시, 40초유지후재실행, 강제종료잠금파일남긴채2개, dev↔exe혼합순서) 전부 "두개생존"0건. Windows서는잠금보유프로세스가파일핸들공유삭제불가로열어stale판정나도삭제안됨 — QLockFile견고하다는Edison판단에동의.
**유력한원인가설**: 앱이안내하는등록명령(stdio_registration_command, app.py:333)은같은emailtomcp.exe를--mcp-stdio-proxy로실행 — Claude Code/Desktop연결돼있으면작업관리자에emailtomcp.exe가GUI1개+프록시(세션당)1개이상으로보이는데**이건정상동작**. --data-dir/EMAILTOMCP_DATA_DIR다른실행도의도적으로공존. **사용자에게두PID의명령줄확인요청권고**: PowerShell `Get-CimInstance Win32_Process -Filter "name='emailtomcp.exe'" | select ProcessId,CommandLine`. 이번수정이그현상을막는다고판단할근거없음 — 재발시명령줄확인+"바인딩실패"로그확인함께필요.
