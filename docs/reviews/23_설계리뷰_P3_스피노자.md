# P3 자동회신 설계 리뷰 — Spinoza (DESIGN.md §7.0~7.11)

## 판정: 수정 후 착수
뼈대는 좋음 — writer 트랜잭션에서 권위판정, 세대번호 DB 단조증가, 판정결과+outbox진입 한 트랜잭션 INSERT 구조로 P2의 H-2·N-1은 구조적으로 막혀있음. High 2건은 문서만 고치면 되는 수준이라 반영 후 Edison에게 넘기면 됨.

## High

**H-A. auto_send 레이트리밋·쿨다운이 `sent` 기준이라 M-1과 같은 함정 잔존 (§7.7, §7.3의 12·13번, G7 ⑥)**
- §7.7이 auto_send 상한을 `drafts.status='sent' + sent_at`으로 집계. 동시성2에서 잡A가 G7에서 outbox로 커밋된 뒤 아직 미발송 상태에서 잡B의 G7 실행 시 A가 집계에 안 잡혀 같은 수신자에게 2건 발송(쿨다운 24시간·1건 위반).
- P2 MCP send_draft에서 고친 "approved_at 기준 모든 상태 집계" 방식이 auto_send 쪽엔 미반영. §7.10의 M-1 행은 "DB로 집계"만 말하고 무엇을 세는지가 빠져 겉으로만 대응.
- 수정: `approved_by='policy_auto_send'` 초안을 approved_at 기준으로 outbox/sending/sent/failed/send_unknown 전체 집계. LoopGuard 12(스레드횟수)·13(쿨다운)도 동일기준. 14번(강등포함)은 auto_reply_log 기준 명시.

**H-B. trusted_authserv_id 자동탐지를 공격자가 오염시킬 수 있음 (§7.6 A1·A2)**
- A1이 "최근 수신 메일 최상단 AR헤더에서 자동탐지"하는데, 주 서비스(네이버/다음/카카오/하이웍스)가 AR을 안 붙일 수 있음(N-04 기존지적). 그런 서비스에서 공격자가 직접 넣은 `Authentication-Results: evil-id; dmarc=pass header.from=partner.com`이 그대로 최상단 AR이 됨.
- 결과: (1)자동탐지가 공격자 id를 제안→사용자확인시 G0 신뢰 오염 (2)실제 authserv-id를 알아낸 공격자가 그 값으로 위조AR을 넣어도 "최상단" 조건 통과.
- 사용자 설정값 자체가 메일내용 영향을 받는 경로 — G7에서 재계산해도 다시 읽는 값이 오염돼있으면 무의미.
- 수정: 신뢰할 AR은 수신MTA가 붙인 Received헤더보다 위쪽(전송중 끼워넣기 불가 위치)일 때만 인정. 자동탐지는 서로다른 발신도메인 메일 N건 이상에서 같은위치·같은id가 나올 때만 후보제시. 그 계정이 AR을 붙이는지(P1 실측) 확정 전엔 A1 자동탐지 비활성.

## Medium

**M-A. G7-G8 사이(최대1시간 TTL) 재검증 안 하는 항목 있음**
- G8은 gate·세대·autosend_state·TTL만 확인. G7 이후 trusted_authserv_id 변경/규칙수정(rule_version 전달 여부 미명시)/레이트리밋 변경에도 이미 outbox인 건은 발송됨 — §7.6 "authserv_id 바꾸면 큐에 바로 반영" 약속과 어긋남.
- 수정: G8에서 job→rule_version을 gate에 전달+AuthGate 재계산, 또는 설정저장 트랜잭션에서 origin=autoreply outbox를 draft로 되돌림(끄기1c와 동일 드레인).

**M-B. G8 분기기준이 origin이라 사람이 보내는 경우와 충돌**
- G8이 "origin=autoreply면" 검사하는데, §7.0은 강등/되돌림된 draft를 "사람이 직접 보낼 수 있다"고 함. 토글off 상태로 사람이 [보내기] 누르면 G8이 다시 draft로 되돌려 영원히 못 보냄. 반대로 failed→outbox재시도/Outbox가상폴더[편집] 뒤에도 approved_by='policy_auto_send' 잔존시 I1 집계·감사기록 오염.
- 수정: G8 분기기준을 approved_by='policy_auto_send'로 변경. origin=autoreply 초안이 draft로 돌아갈 때마다 approved_by 초기화. outbox [편집] 전이를 전이표에 명시.

**M-C. G7이 잡상태와 G5해시에 안 묶여있음**
1. G7①에 잡 status 확인 없음 — 긴급정지는 세대 안 올리고 잡만 cancelled. 늦게 도착한 G7이 cancelled잡을 done으로 덮어쓰고 draft 생성 가능 → 수정: `WHERE status='running' AND submitted_at IS NOT NULL` CAS조건 추가.
2. ⑦이 "넘긴 본문해시=INSERT할 본문해시"만 비교 — 트랜잭션 안에서 읽은 jobs.submission_sha256과 비교해야 G5~G7 바이트 동일성 보장.
3. GuardResult·PreflightResult가 호출자 전달값이라 위조/다른본문결과 전달 가능 → 수정: GuardResult에 body_sha256 포함, G7에서 대조.

**M-D. `verify: Callable` 주입은 I-1을 형태만 바꾼 것 (§7.10 I-1행)**
- 필수 키워드 인자여도 `lambda c,j: OK` 전달시 검사 생략됨. 수정: 권위판정 함수를 repo 안에서 고정호출하거나, 아키텍처테스트로 "주입구현은 단 하나" 강제.

**M-E. 숨은 신뢰지점: G6은 claude 프로세스 자기보고 stream을 신뢰**
- 설정격리 폴백3(§2(c) "둘다불가능하면 R10수용")에서 사용자 hooks·플러그인이 잡토큰+env를 가진채 실행가능 — 이 경우 stream 도구목록이 검증근거 못 됨. A8은 실행전 1회점검(TOCTOU)을 러너가 전달하는 값이라 구체성 부족.
- 수정: 폴백3 상태에서는 auto_send 금지, draft만 허용. A8의 점검항목·시점·결과구조(잡ID·시각 바인딩)를 §7.11에 명시.

## Low
- **L-A**: 끄기에 CAS 걸리면 안 됨. `set_enabled(enabled, *, expected_generation)` 시그니처가 끄기에도 CAS 요구하는 것으로 읽힘 — 끄기는 안전방향이라 무조건 성공해야 함.
- **L-B**: 세대0 의미 고정 필요(ABA방지조건). 마이그레이션 `enable_gen DEFAULT 0`과 초기 generation값이 안 겹쳐야 함 — "ON상태 세대는 항상 1이상", generation키 없거나 형식오류면 fail-closed 명시 필요(지켜지면 ABA는 막힘).
- **L-C**: 출력가드 입력이 실제발송 MIME과 같아야 함. 출력가드 입력=제출본문, 실제MIME=제목·고지문·서명 붙은것 — 붙는블록이 상수/G0설정값뿐임을 명시 필요.
- **L-D**: principal판정을 닫힌enum으로. L3의 principal.kind는 닫힌enum이어야 하고, 토큰조회시 job저장소↔mcp_tokens 사이 폴백조회 없어야 함(분리 자체는 설계상 명확).

## 질문별 결론 요약
1. §7.10 대응표: H-2·N-1·N-4·L1/L2 타당. M-1은 겉으로만 대응(H-A). I-1 부분대응(M-D). H-1은 outbox[편집]경로 빠짐(M-B).
2. G7-G8 사이: 세대교체는 G8에서 막힘. 인증·규칙변경은 안 막힘(M-A). J/대화형토큰 분리는 충분(L-D만 확인).
3. 토글순서: "DB먼저닫고 런타임멈춤" 순서 안전. 커밋~토큰폐기 사이 get_job_message 읽을 틈 있으나 G5에서 거부돼 무해. ABA는 L-B조건 지키면 막힘.
4. AuthGate 재계산: 다시읽는 값 자체가 메일로 오염가능(H-B).
5. "신뢰부여는 G0 하나뿐" 원칙: H-B(자동탐지)와 M-E(G6 자기보고, A8)가 숨은 신뢰지점.
