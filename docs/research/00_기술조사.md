## 1. Claude Code CLI headless — 공식 문서 기준 확인 결과

출처: [CLI reference](https://code.claude.com/docs/en/cli-reference), [Run Claude Code programmatically(headless)](https://code.claude.com/docs/en/headless), [Connect to tools via MCP](https://code.claude.com/docs/en/mcp)

### 1.1 설계서가 확인을 요청한 플래그 — 전부 **존재 확인됨**
| 플래그 | 확인 결과 |
|---|---|
| `-p`/`--print` | 존재. 비대화형 실행, `-p "query"` |
| `--mcp-config` | 존재. JSON 파일/문자열(공백 구분 다중 가능)로 MCP 서버 로드. `-p`와 함께 쓰면 대기 중인 서버 연결을 기다림(기본 `MCP_TIMEOUT` 30초) |
| `--strict-mcp-config` | 존재. `--mcp-config`로 전달한 서버만 쓰고 나머지 MCP 설정(프로젝트 `.mcp.json`, 플러그인 MCP, claude.ai 커넥터)은 무시 |
| `--allowedTools`(`--allowed-tools`) | 존재. 프롬프트 없이 실행되는 도구 목록. 패턴 매칭 지원(`Bash(git log *)` 등) |
| `--disallowedTools`(`--disallowed-tools`) | 존재. 거부 규칙. **중요**: 맨 이름(`"Edit"`)은 해당 도구 자체를 Claude 컨텍스트에서 제거, `"*"`는 전체 도구 제거, **`"mcp__*"`는 모든 MCP 도구를 제거**한다고 공식 문서에 명시됨(아래 1.4 참조) |
| `--append-system-prompt` | 존재. 기본 시스템 프롬프트 뒤에 텍스트 추가(대화형/비대화형 모두 적용) |
| `--output-format json` | 존재. `text`/`json`/`stream-json` 중 선택. JSON 응답에 `result`(텍스트), `session_id`, `total_cost_usd`(모델별 비용 분해 포함) 등 메타데이터 포함 — **`is_error`/`num_turns` 필드명은 공식 문서 본문에서 직접 명명된 걸 확인하지 못함(서드파티 요약 글들은 `is_error`를 언급하나 1차 출처에서 재확인 필요 — "미확인", Phase 3 전에 실제 `--output-format json` 1회 실행해 실물 JSON 스키마를 캡처해 둘 것을 권고)** |
| `--max-turns` | 존재. `-p` 모드 전용, 에이전틱 턴 수 제한, 초과 시 에러로 종료 |
| `--setting-sources` | 존재. **쉼표 구분 문자열**(`user,project,local`) — 설계서 예시의 공백/별도 토큰 형태(`--setting-sources ""`)가 "전부 비움"으로 동작하는지는 문서에 명시돼 있지 않음(빈 문자열 처리 "미확인", 실측 필요) |
| `--permission-mode` | 존재. `default`/`acceptEdits`/`plan`/`auto`/`dontAsk`/`bypassPermissions`/`manual`(=default 별칭) |

### 1.2 MCP 도구명 형식 `mcp__<server>__<tool>` — **확인됨**
- 공식 패턴: `mcp__<server>__<tool>`. 플러그인 내장 서버는 `mcp__plugin_<plugin-name>_<server-name>__<tool-name>` 형태(design에는 해당 없음, 단일 MCP 서버이므로 `mcp__emailtomcp__<tool>` 형태가 맞다)
- `A-Z a-z 0-9 _ -` 이외 문자는 `_`로 치환됨

### 1.3 http 타입 MCP 서버 + headers 설정 — **확인됨, 설계서 예시와 일치**
```json
{
  "mcpServers": {
    "emailtomcp": {
      "type": "http",
      "url": "http://127.0.0.1:<port>/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```
- CLI 등록: `claude mcp add --transport http emailtomcp http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"` — 설계서 §6.1의 명령과 동일, 확인됨.
- 참고로 토큰이 동적으로 바뀌는 경우 `headersHelper`(실행형 스크립트)도 지원하나, 설계서의 "잡 토큰은 메모리에만, mcp.json 파일 0600"에는 영향 없음.

### 1.4 `--disallowedTools`가 MCP 도구에 영향을 못 준다는 과거 버그 — **상충 정보, 보수적으로 접근 권고**
- GitHub 이슈 [#12863](https://github.com/anthropics/claude-code/issues/12863) "[BUG] --disallowedTools flag does not affect MCP server tools"는 `-p` 모드에서 `--disallowedTools`가 MCP 도구를 막지 못한다고 보고.
- 반면 현재(2026-10) 공식 CLI reference는 `"mcp__*"`를 disallowedTools에 넣으면 "모든 MCP 도구를 제거한다"고 명시 — 이슈가 이미 수정됐거나, 이슈 보고 당시 버전의 특정 상황이었을 가능성.
- **설계서에는 실질적 영향 없음**: 설계서가 `--disallowedTools`에 넣는 항목은 Bash/Edit/Write 등 **빌트인 도구**뿐이고 MCP 도구는 `--allowedTools` 화이트리스트로만 통제한다. 즉 이 버그(해소 여부 불문)와 무관하게 설계는 안전하다. 다만 **Phase 3에서 설치된 실제 CLI 버전으로 "허용 목록 외 MCP 도구를 호출 시도했을 때 실제로 거부되는지"를 반드시 실측 회귀 테스트할 것**을 권고(§13 R1에 하위 항목으로 추가 권고).

### 1.5 headless에서 MCP 도구를 승인 프롬프트 없이 쓰는 방법 — **확인됨**
- `-p` 세션은 워크스페이스 신뢰 다이얼로그도, 서버별 승인 프롬프트도 띄우지 않는다("A `-p` session shows no workspace trust dialog and no per-server approval prompt").
- 따라서 **`--allowedTools`에 정확한 `mcp__emailtomcp__<tool>` 이름을 나열하면 그 도구들은 프롬프트 없이 자동 승인되어 실행**된다. 이것이 설계서가 쓰는 방식이고, 공식 문서로 뒷받침된다.
- 허용 목록에 없는 도구(혹은 거부되는 호출)는 `-p`에 응답할 "host"가 없으면 **거부(deny)**된다 — `--permission-prompts none`을 명시하면 이 거부 동작과 "재시도하지 말라"는 안내가 Claude에게 더 명확히 전달된다. **권고: job 호출에 `--permission-prompts none`을 추가**(현재 설계서 §2(c) 커맨드 예시에는 없음 — 반영 권고).

### 1.6 `--bare` 모드 — **설계서에 반영되지 않은 중요 신규 사실 (설계 충돌 가능성)**
- `--bare`는 hooks/skills/커스텀 커맨드/서브에이전트/설치된 플러그인/MCP 서버/자동 메모리/CLAUDE.md 자동탐색을 모두 스킵해 시작 속도를 높인다. 공식 문서: **"스크립트·SDK 호출에 권장되는 모드이며, 향후 `-p`의 기본값이 될 예정"**.
- 그러나 **"bare 모드는 OAuth 자격증명이나 시스템 키체인을 전혀 읽지 않는다. Anthropic API에는 `ANTHROPIC_API_KEY`를 환경변수로 설정해야 한다"**고 명시돼 있다.
- **설계서 §2(c)는 "구독 로그인(headless)으로 처리하고 `ANTHROPIC_API_KEY`는 기본 제거한다"는 전제다 — 이는 `--bare`와 정면으로 충돌한다.** `--bare`를 쓰면 구독 로그인이 통하지 않고, `--bare`를 안 쓰면(현재 설계대로) `-p`가 프로젝트/사용자 레벨 hooks·MCP·CLAUDE.md·플러그인까지 전부 로드한다(단, 잡 cwd가 빈 임시폴더이므로 "프로젝트" 스코프 설정은 없지만, **사용자(`~/.claude`) 레벨 설정·hooks·플러그인·MCP 서버는 여전히 로드된다** — `--strict-mcp-config`가 막는 것은 프로젝트 스코프 MCP·플러그인 MCP·claude.ai 커넥터이며, 사용자 스코프에 등록된 MCP 서버까지 막는지는 문서에서 명확히 확인하지 못함, "미확인").
- **설계서 수정 권고(§2(c), §13 R1/R2)**: ①`--bare`는 쓰지 않는다(구독 로그인 유지 목적과 상충하므로) — 이 판단 자체를 설계서에 명시적으로 적어둘 것. ②대신 사용자 레벨에서 로드될 수 있는 hooks/플러그인/MCP가 job 실행에 영향을 주지 않는지 Phase 3에서 실측 확인할 것(사용자 홈의 `~/.claude/settings.json`에 등록된 다른 MCP 서버·hook이 job 세션에 섞여 들어올 위험 — LoopGuard/프롬프트 인젝션 방어와는 별개의 "환경 오염" 리스크로 R10 신설 권고).

### 1.7 ANTHROPIC_API_KEY 우선순위 — **확인됨(단, 전제와 상충 지점 있음)**
- 인증 우선순위(상위→하위): 클라우드 제공자 ambient credential(Bedrock/Vertex) → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` → `apiKeyHelper`(stdout으로 토큰 출력하는 실행파일). (출처: WebSearch 요약, 공식 1차 문서 페이지 자체는 확인 못함 — "부분 확인")
- **구독과 API 키가 동시에 있으면 API 키가 우선 적용되어 이중 과금될 수 있다**는 경고가 커뮤니티/공식 가이드에 있음 — 설계서가 "자식 프로세스 환경에서 `ANTHROPIC_API_KEY`를 기본 제거"하는 방침은 이 문제를 정확히 막기 위한 올바른 조치로 확인됨(계속 유지 권고).
- `claude auth status`(JSON)로 `authMethod`(`none`/`claude.ai`/`oauth_token`/`api_key`/`api_key_helper`/`third_party`) 확인 가능 — 앱의 "Claude/MCP 패널"(§11.5)에 CLI 버전뿐 아니라 **이 인증방식도 같이 보여주는 것을 권고**(사용자가 구독 로그인 상태인지 한눈에 확인 가능).

### 1.8 결론 요약 (설계서 수정 필요 지점)
- §2(c) 커맨드 블록: `--setting-sources ""` 가 실제로 지원되는지 "미확인" 표기 유지, Phase 3에 실측 필요. `--permission-prompts none` 추가 권고.

## 2. MCP Python SDK(공식 `mcp` 패키지) — **중대한 변경사항 확인(설계서 수정 필수)**

출처: [PyPI mcp](https://pypi.org/project/mcp/), [GitHub modelcontextprotocol/python-sdk](https://github.com/modelcontextprotocol/python-sdk), [공식 문서 py.sdk.modelcontextprotocol.io](https://py.sdk.modelcontextprotocol.io/), [v1→v2 마이그레이션 가이드](https://py.sdk.modelcontextprotocol.io/migration/), [ASGI 실행 가이드](https://py.sdk.modelcontextprotocol.io/run/asgi/), [Authorization 가이드](https://py.sdk.modelcontextprotocol.io/run/authorization/)

### 2.1 최신 버전 — **확인됨**
- PyPI `mcp` 최신: **2.3.0 (2026-10-02 공개)**. 이전 릴리스: 2.2.0(2026-09-07), 2.1.1/2.1.0(2026-08), 2.0.1(2026-08-26), **2.0.0(2026-07-28, v2 메이저 릴리스 — MCP 2026-07-28 스펙 개정판에 맞춤)**.
- v1 라인은 1.29.0에서 종료. v2는 1.x와 **하위호환이 끊긴 메이저 변경**이다.

### 2.2 `FastMCP` → `MCPServer` 리네임 — **설계서 전체에 영향, 반드시 수정 필요**
- MCP SDK v2에서 **`FastMCP` 클래스가 `MCPServer`로 이름이 바뀌었고, 모듈 경로도 `mcp.server.fastmcp` → `mcp.server.mcpserver`로 바뀌었다.**
- **하위호환 별칭 없음** — v2에서 `mcp.server.fastmcp`를 import하면 마이그레이션 가이드로 안내하는 `ModuleNotFoundError`가 발생한다(스텁 모듈).
- 설계서 §6.1("`mcp` 공식 Python SDK의 FastMCP로 만들고")와 §10(라이브러리 표 "FastMCP, streamable HTTP")는 **현재 최신 버전(2.3.0) 기준으로 틀린 이름**이다. `MCPServer`(import `from mcp.server.mcpserver import MCPServer`)로 전면 수정 필요.
- 단, v1(`mcp>=1.28,<2`)으로 고정해 FastMCP를 계속 쓰는 선택도 가능하지만, 신규 프로젝트가 처음부터 레거시 버전에 고정하는 것은 권장되지 않음 — **v2/MCPServer로 설계하는 것을 권고**.

### 2.3 streamable HTTP / stateless 옵션 — **확인됨, API 위치 변경**
- v1: `FastMCP("Demo", json_response=True, port=9000)`처럼 생성자에 전달.
- v2: 생성자는 이름만 받고(`MCPServer("Demo")`), `host/port/json_response/stateless_http/transport_security/event_store/max_request_body_size` 등은 **`run()` 또는 `streamable_http_app()` 호출 시점**으로 이동.
- `app = mcp.streamable_http_app(stateless_http=True, json_response=True)` 형태로 Starlette ASGI 앱을 얻어 `uvicorn.run(app, host="127.0.0.1", port=8765)`로 띄우는 설계서 방식은 **여전히 유효**(메서드 자체는 존재), 다만 인자 전달 위치가 바뀐 걸 반영해야 한다.
- **같은 `streamable_http_app()`이 2025년대 클라이언트의 `initialize` 요청과 2026-07-28 신규 스펙(스테이트리스화) 요청을 모두 처리** — 별도 분기 불필요.

### 2.4 ASGI 미들웨어로 Bearer 인증 — **확인됨, 두 가지 방식 혼용 가능**
- (a) SDK 자체 지원: `TokenVerifier` 프로토콜(비동기 `verify_token(token) -> AccessToken | None`)과 `AuthSettings`(요구 scope 지정, 리소스 바인딩 검증 `validate_token_resource`)를 제공 — OAuth 2.1 리소스서버 패턴에 맞춰져 있음.
- (b) 설계서가 쓰려는 방식(단순 `hmac.compare_digest` Bearer 비교): SDK가 Starlette 기반이므로 **표준 ASGI 미들웨어**(`Starlette` `Middleware` 클래스)로 감싸 모든 요청을 가로채는 방식도 그대로 가능 — 공식 문서가 전제하는 OAuth 패턴보다 단순하지만 기술적으로 문제 없음.
- **주의(설계 반영 필요)**: `streamable_http_app()`이 돌려주는 앱을 다른 Starlette 앱에 **mount**하거나 커스텀 미들웨어로 감싸면, **SDK 내장 lifespan이 비활성화된다** — 이 경우 호스트(미들웨어 래퍼) 쪽 lifespan에서 반드시 `async with mcp.session_manager.run():`을 직접 열어줘야 하며, 안 그러면 "첫 요청이 실패"한다고 공식 문서가 명시. 설계서 §6.1에 **이 lifespan 관리 책임을 Backend 스레드 시작 코드에 명시적으로 추가**할 것을 권고.
- 헤더/토큰 접근: `get_http_headers()`로 현재 요청의 HTTP 헤더(Authorization 등) 조회 가능. 커스텀 상태 저장은 `context.fastmcp_context.set_state()` 패턴(네이밍이 v1 FastMCP 잔재일 수 있어 v2 `MCPServer`에서 동일한지는 "미확인" — 구현 시 재검증 권고).

### 2.5 list_tools 동적 스코프 필터링 — **SDK에 내장 기능 없음, 직접 구현 필요(설계서 방향 정확함)**
- 공식 authorization 가이드: "토큰 스코프별 도구 노출 제어 기능은 SDK에 내장돼 있지 않다." `get_access_token()`으로 호출자의 scope를 읽어 **"그 지점이 바로 도구별 규칙을 직접 구현해 거부할 지점"**이라고 안내.
- 즉 설계서 §6.1 "도구 노출 범위: 토큰 스코프에 따라 도구를 제한한다. list_tools와 call_tool 양쪽에서 모두 검사한다"는 **SDK 레벨에선 저수준 handler(`on_list_tools`/`on_call_tool` 커스텀 콜백, v2에서는 생성자 키워드 인자로 등록 — v1의 `@server.on_list_tools` 데코레이터 방식에서 변경됨)를 직접 작성해야 한다**는 뜻이며, 이는 Edison 구현 시 반드시 알아야 할 v2 API 변경점이다.

### 2.6 DNS rebinding 보호 / transport security — **확인됨, 설계서가 과소평가하고 있을 가능성**
- v2는 **`127.0.0.1`/`localhost`/`::1`에 대해 DNS rebinding 보호가 기본 활성화**되어 있다("Auto-enabled for 127.0.0.1/localhost/::1"). 커스터마이즈는 `transport_security=TransportSecuritySettings(allowed_hosts=..., allowed_origins=...)`로 전달.
- 참고(과거 취약점): [CVE-2025-66416](https://advisories.gitlab.com/pypi/mcp/CVE-2025-66416/) — "MCP Python SDK는 기본적으로 DNS rebinding 보호를 활성화하지 않는다"는 보안 권고가 **v1 계열**을 대상으로 존재했음. v2는 이를 기본 활성화로 바꿔 대응한 것으로 보인다(정확한 버전 경계는 "미확인" — v2.0.0 변경사항인지 더 구체적 CVE 수정 커밋을 특정하지 못함).
- 설계서 §6.1·§8은 "Origin 거부, Host 검사"를 **자체 코드로 직접 구현**하는 전제인데, **v2 SDK가 기본 제공하는 `transport_security` 설정과 중복되거나 충돌할 수 있다** — Edison 구현 시 SDK 기본 보호와 자체 검증 로직의 역할 분담을 명확히 할 것을 권고(중복 구현 자체는 안전 측면에서 나쁘지 않으나, 설정값 불일치로 둘 중 하나가 더 느슨하게 동작하지 않도록 확인 필요).

### 2.7 MCP 스펙의 보안 권고(Origin/localhost) — **확인됨**
출처: [MCP Transports - Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [Security Best Practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)
- "서버는 모든 수신 연결에 대해 Origin 헤더를 검증해야 한다(MUST)"(DNS rebinding 방지).
- "Origin 헤더가 있는데 유효하지 않으면 403을 반환해야 한다(MUST)".
- "로컬 실행 시 서버는 모든 인터페이스(0.0.0.0)가 아니라 localhost(127.0.0.1)에만 바인딩해야 한다(SHOULD)".
- "loopback(127.0.0.1/::1)으로 들어온 연결이라도 Host 헤더가 non-localhost이면 403으로 거부"하는 구체적 구현 패턴도 권고됨.
- **설계서 §6.1·§8의 "127.0.0.1 고정, Origin 거부, Host 검사"는 MCP 공식 스펙 권고와 정확히 일치한다 — 이 부분은 그대로 유지.**

### 2.8 결론 요약 (설계서 수정 필요 지점)
- §6.1, §10: **`FastMCP` → `MCPServer`**(`mcp.server.mcpserver`)로 전면 수정, 버전은 `mcp>=2.3,<3`(또는 그 시점 최신) 명시 권고.
- §6.1: `streamable_http_app()`에 커스텀 Bearer 미들웨어를 씌울 경우 **`mcp.session_manager.run()`을 호스트 lifespan에서 직접 열어야 한다**는 제약을 구현 노트에 추가.
- §6.1: list_tools/call_tool 스코프 필터링은 SDK 내장 기능이 아니라 v2 저수준 handler(생성자 키워드 등록 방식)로 직접 구현해야 함을 명시.
- §6.1/§8: SDK 기본 `transport_security`(DNS rebinding 보호, v2부터 기본 on)와 자체 Origin/Host 검증 로직의 관계를 명확히 할 것.

### 3.2 추천안

**Velopack을 1순위로 권고한다.** 근거:
1. **설계서가 이미 선택한 "PyInstaller onedir"와 정확히 맞물린다** — tufup/DIY는 패키징 방식에 무관하지만 Velopack은 onedir를 요구조건으로 명시, 재작업 없음.
2. **Win+macOS 단일 솔루션** — WinSparkle/Sparkle처럼 OS별 다른 네이티브 라이브러리를 각각 통합할 필요가 없다. 설계서의 "하나의 코드베이스, 두 OS 지원" 원칙에 가장 부합.
3. **GitHub Releases가 1급 배포처로 명시 지원**되고, 델타 업데이트·롤백까지 기본 제공되어 tufup/DIY보다 구현 범위가 작다.
4. **활발히 유지보수**(2026-09 릴리스) — PyUpdater(단종)의 대안으로 흔히 언급되는 tufup보다도 최근 활동이 많고, 크로스플랫폼 데스크톱 앱 자동 업데이트가 주목적인 전용 도구라 범용성이 높다.
5. 단점(감수 필요): **`vpk` 패키징 CLI가 .NET SDK 의존** — GitHub Actions Windows/macOS 러너에는 .NET SDK가 기본 설치돼 있어 큰 부담은 아니지만, 로컬 개발자 머신에도 .NET SDK 설치가 필요해진다. 또한 Python API(`velopack.App().run()`, `UpdateManager`)의 세부 동작(코드서명과의 상호작용, private repo 토큰 처리, 정확한 롤백 절차)은 이번 조사에서 전부 확인하지 못했다(깊은 레퍼런스는 "미확인" — Edison 착수 전 `docs.velopack.io`의 `distributing/overview`, `integrating/overview` 하위 페이지를 추가로 봐야 한다).

차선책: **tufup**(보안설계가 TUF에 위임되어 더 엄격하지만, GitHub Releases를 업데이트 서버로 직접 쓰는 레시피가 없어 구현량이 더 많음) 또는 **DIY+SHA256**(가장 단순하지만 Windows exe 교체용 헬퍼 프로세스와 서명검증을 전부 자체 구현해야 함, 델타 업데이트 없음).

**비추천**: PyUpdater(단종), WinSparkle/Sparkle(OS별 이원화로 설계서 원칙과 배치).

### 3.3 GitHub API rate limit / private repo 토큰 — **확인됨**
출처: WebSearch 종합(GitHub 공식 rate limit 정책 일반 지식과 일치)
- 비인증 요청: **시간당 60회**. 인증(PAT) 요청: **시간당 5,000회**.
- `/repos/{owner}/{repo}/releases/latest`는 **public repo면 비인증으로 접근 가능**하지만, **private repo는 반드시 토큰(personal access token 등) 필요**.
- 앱이 자동 업데이트 체크를 polling식으로 자주 하면(예: 매 시간) 비인증 60회/시간 한도 안에 들어오지만, 여러 사용자 PC가 같은 공인 IP(NAT)를 공유하면 한도를 쉽게 넘길 수 있음 — **앱 배포용 repo를 public으로 둘 계획이면 문제 적음. private으로 둘 계획이면 업데이트 체크용 토큰(읍은 권한, repo:read 정도)을 앱에 내장해야 하는데, 이는 "클라이언트에 토큰을 내장"하는 보안 트레이드오프**가 생긴다. 설계서 v0.2에 **"배포 repo를 public/private 중 무엇으로 할지"를 Q8로 신설해 사용자에게 확인**할 것을 권고.

### 3.4 GitHub Actions 매트릭스 빌드 → 태그 푸시 시 Release 자동 생성 — **확인됨(사례 다수)**
- 일반 패턴: `on: push: tags: ['v*']` → `strategy.matrix.os: [windows-latest, macos-latest]`(또는 macOS arm64/x64 분리) → PyInstaller 빌드 → SHA256 생성 → `softprops/action-gh-release`류 액션으로 해당 태그의 Release에 자산 업로드.
- 참고 사례: [Build a multi-OS Python app on GitHub Actions](https://data-dive.com/multi-os-deployment-in-cloud-using-pyinstaller-and-github-actions/), [Building PyInstaller app for multiple OSs](https://www.alexjcoleman.me/blog/2023-03-28-building-your-pyinstaller-app-for-multiple-oss-with-github-actions.html) 등 — 다만 Velopack `vpk` 특화 Actions 워크플로 사례까지는 구체적으로 확보하지 못했다("미확인", Phase 5에서 공식 Velopack Actions 예제를 다시 찾아볼 것).

### 3.5 코드서명/notarization과의 관계
- macOS: notarization 없이 배포된 앱은 Gatekeeper 경고가 뜨고, Velopack/tufup/DIY 무엇을 쓰든 **서명·notarization 자체는 각 업데이트 솔루션이 대신해주지 않는다** — 빌드 파이프라인에서 별도로 `codesign`/`notarytool`을 돌려야 한다(설계서 §9.2가 이미 인지하고 있음, 자동 업데이트 방안과는 독립적 작업임을 명확히 할 것).
- Windows: 코드서명이 없으면 SmartScreen 경고. Velopack/DIY 모두 서명 자체는 대신하지 않음.

## 4. 버전 관리

### 4.1 단일 버전 소스 방식 비교 — **확인됨**
- **importlib.metadata 방식**: 설치 시점의 메타데이터를 읽음 — 런타임에 빠르지만, "설치 당시" 값이라 editable/frozen 환경에서 최신 git 상태를 반영 못할 수 있고 METADATA 파싱이 상대적으로 느릴 수 있음(공식 pyOpenSci 가이드).
- **hatch-vcs/setuptools-scm(git 태그 기반)**: 빌드/설치 시점에 git 태그로부터 버전을 자동 산출해 `_version.py`(hatch-vcs) 등으로 기록 — "소스를 안 건드려도 태그만 찍으면 버전이 바뀐다"는 장점, 단 **git 태그가 없는 clone/CI 캐시 환경에서 버전이 어긋나는 사고가 흔함**(hatch-vcs-footgun-example 등 이슈들이 이를 다룸).
- **PyInstaller로 번들된 앱에서는 둘 다 함정이 있다**: importlib.metadata는 "설치된 패키지의 dist-info"를 찾는데, PyInstaller onedir 번들 안에는 일반적인 `site-packages`/`dist-info` 구조가 없어 **그대로는 동작하지 않는다**(번들 시점에 버전 문자열을 리소스 파일 등으로 별도로 박아 넣어야 함) — 이 문제는 명시적으로 "PyInstaller 번들에서 importlib.metadata가 실패한다"는 1차 자료를 확보하지 못했으나("미확인", 일반적으로 알려진 PyInstaller 패턴/`_version.py` 생성형 접근의 존재 이유 자체가 이 문제를 우회하기 위함과 일치) — **권고: hatch-vcs의 "build hook으로 `_version.py` 파일을 생성"하는 방식을 쓰고, 이 정적 `_version.py`를 PyInstaller가 그대로 번들링하게 하는 편이 importlib.metadata 런타임 조회보다 안전**하다.
- 0.0.0에서 시작하는 설계서 전제와는 **hatch-vcs/setuptools-scm이 자연스럽게 맞는다** — 태그가 없으면 보통 `0.0.0` 혹은 `0.1.dev...`류 값이 나오므로, 명시적으로 `v0.0.0` 태그를 하나 찍어두고 시작하는 것을 권고.

### 4.2 SemVer 비교 라이브러리 — **확인됨**
- 공식 패키징 생태계 표준은 **`packaging.version.Version`**(PyPA 공식, PEP440 기준이지만 SemVer와 거의 호환) — 이미 다른 파이썬 패키징 도구들의 표준이라 추가 의존성 부담이 적음(pydantic, pip 등도 내부적으로 씀).
- 순수 SemVer(접두사 `v`, `-rc.1` 등) 엄밀 비교가 필요하면 `semver` PyPI 패키지(`semver.compare`) 선택 가능.
- **권고**: 업데이트 체크(현재 버전 vs GitHub 최신 릴리스 태그 비교)에는 `packaging.version.Version`으로 충분 — 별도 `semver` 의존성 추가 불필요.

### 4.3 PyInstaller 번들에서 버전 읽기 주의점 — **확인됨(부분)**
- Windows: `--version-file`로 exe에 버전 리소스(FileVersion/ProductVersion 등)를 심는 공식 옵션 존재.
- macOS: **`pyinstaller` CLI에는 CFBundleShortVersionString을 지정하는 커맨드라인 옵션이 없다**("it is not currently possible to set the value of CFBundleShortVersionString from the command line, it will always default to 0.0.0") — `.spec` 파일의 `BUNDLE(..., version=...)` 인자나 `info_plist={"CFBundleShortVersionString": ..., "CFBundleVersion": ...}` 딕�셔너리로 직접 지정해야 한다. **설계서 §9.2(패키징)에 이 macOS 특이사항을 명시해 둘 것을 권고** — CI에서 빌드 시점에 `.spec` 파일을 템플릿화해서 버전 문자열을 주입하는 스텝이 필요하다는 뜻.

### 5.1 설계서 R3/Q3/MVP 전략에 대한 중대한 수정 권고
설계서 §13 R3는 "Gmail/M365는 기본 인증을 제한하고 OAuth2를 요구한다 → MVP는 앱 비밀번호로 시작하고 OAuth2는 P5에 넣는다"고 되어 있다. 이번 조사로 **이 전제가 서비스별로 다르게 틀렸다는 게 확인됐다**:
- **Gmail**: 앱 비밀번호가 **현재도 유효**(2FA 활성화 전제) — "MVP는 앱 비밀번호로 시작" 전략이 **그대로 유효**.
- **Microsoft 365/Outlook.com**: IMAP/POP는 **이미 2022년에** Basic Auth가 막혔다 — "앱 비밀번호로 MVP 시작"이 **IMAP/POP 계정에는 아예 통하지 않는다.** SMTP만 한시적으로 봐주고 있으나 이마저 2026년 말로 끝이 보인다. **즉 M365/Outlook.com은 OAuth2를 P5로 미룰 수 없고, 처음부터(또는 최소 "지원 안 함" 명시가 필요한) 범위에 포함해야 한다.**
- **네이버/카카오/다음**: 역시 2025년부로 **일반 비밀번호 로그인이 전면 차단**되고 **2FA+앱비밀번호가 필수**가 됐다 — 설계서가 "앱 비밀번호" 전략을 쓰는 것 자체는 맞지만(네이버/카카오/다음 모두 앱비밀번호는 지원), **"2FA를 켜야 앱 비밀번호를 만들 수 있다"는 전제조건을 UI 안내문구(계정 설정 화면, §11.3)에 명시해야** 사용자가 헷�갈리지 않는다.
- **하이웍스**: IMAP을 지원하지 않으므로, 계정 설정 UI의 "새 계정 기본값은 IMAP" 정책(§2(b))이 하이웍스에는 적용될 수 없다 — **하이웍스 선택 시 자동으로 POP3를 강제**하거나 경고를 띄우는 분기가 필요.

**결론(설계서 수정 지점)**: §13 R3를 "Gmail은 앱비밀번호로 MVP 가능, M365/Outlook.com은 IMAP/POP가 이미 OAuth2 필수(앱비밀번호 전략 불가) — P5로 미룰 수 없는 범위" 식으로 서비스별로 분리해 재작성. §11.3 프리셋에 **하이웍스를 추가**하고 "IMAP 미지원·POP3 강제" 로직 반영, 네이버/카카오/다음 프리셋에는 "2FA+앱비밀번호 필요" 안내문 추가. Q3("주로 쓸 메일 서비스")의 답이 M365/Outlook.com이라면 OAuth2 작업을 Phase 5에서 더 앞당겨야 한다는 점을 사용자에게 알려야 함.

## 6. 기타 검증

### 6.1 PySide6 + PyInstaller 호환 Python 버전 — **확인됨**
- PySide6 **6.11.0**부터 최소 지원 Python이 **3.10**으로 상향(과거 3.8 지원 중단, [GitHub 이슈 #780](https://github.com/freedomofpress/dangerzone/issues/780) 참고 사례). PySide6 **6.10.1**부터 Python 3.14 지원 추가.
- PyInstaller **6.22.3**은 Python 3.8~3.15 전 구간을 지원.
- **결론**: 설계서 §10이 못박은 **Python 3.12**는 PySide6(≥3.10 요구)·PyInstaller(≤3.15 지원) 양쪽 범위에 안전하게 들어간다 — 변경 불필요.

### 6.2 keyring의 PyInstaller hiddenimports 이슈 — **확인됨(알려진 문제, 해결책 명확)**
- `keyring`은 백엔드를 동적 플러그인 방식으로 탐색하는데, **PyInstaller의 정적 분석이 이 동적 임포트를 못 잡아 `KeyError: 'keyring.backends'` 류 런타임 에러가 난다**는 것이 잘 알려진 이슈([jaraco/keyring#399](https://github.com/jaraco/keyring/issues/399), [pyinstaller#4569](https://github.com/pyinstaller/pyinstaller/issues/4569)).
- **단순히 `hiddenimports`에 keyring 서브모듈 이름을 몇 개 나열하는 것만으로는 안 풀리는 경우가 보고됨** — 권고된 해법은 PyInstaller 훅 파일에서 `collect_submodules('keyring.backends')`(및 필요시 `keyring.backends.*`, OS별 백엔드인 `keyring.backends.Windows`/`macOS` 포함)를 호출해 전체 서브모듈을 강제로 수집하는 것.
- **설계서 §9.2에 "keyring/uvicorn 관련 hiddenimports를 지정한다"는 한 줄이 있는데, 구체적으로 `collect_submodules` 기반 훅을 쓰라고 구현 노트에 못박을 것을 권고**(Edison이 "hiddenimports 리스트"만으로 시도하다 막히는 걸 방지).

### 6.3 SQLite FTS5 trigram 토크나이저 — **부분 확인**
- trigram 토크나이저는 **SQLite 3.34.0(2020-12)**에서 코어 기능으로 추가됐다 — 2026년 현재 유통되는 모든 Python 배포판(3.9 이상)의 bundled SQLite는 이보다 훨씬 신버전이라 **버전 자체는 문제가 되지 않을 것으로 추정**되나, **Python 3.12/3.13 공식 Windows/macOS 설치본이 정확히 몇 버전의 SQLite를 번들하는지는 1차 자료로 확인하지 못했다("미확인")** — 플랫폼(Windows 공식 installer vs macOS 공식 installer vs Homebrew)마다 링크하는 SQLite 버전이 다를 수 있으므로, **빌드 파이프라인에서 `python -c "import sqlite3; print(sqlite3.sqlite_version)"`을 실제 빌드 머신에서 실행해 3.34 이상(trigram 가능)인지, 가능하면 3.45 이상(trigram의 `remove_diacritics` 옵션까지 가능)인지 확인하는 체크를 CI에 추가할 것을 권고**.
- 설계서 R7("FTS5가 한글 부분일치를 잘 못 찾는다 → LIKE 폴백, trigram 검토")은 방향이 맞다 — trigram 토크나이저 자체는 한글 완성형에 대해서도 바이트/문자 3-그램 매칭이라 부분일치에 유리하나, 한글 자모 결합 특성상 완벽한 해법은 아니며 "LIKE 폴백 병행"이라는 현재 전략이 합리적이다.

### 6.4 nh3 유지보수 상태 — **확인됨, 양호**
- `nh3`(Mozilla Ammonia Rust 바인딩) 최신 0.3.6, **2026-06-22 릴리스** — 활발히 유지보수됨. Read the Docs 등 프로덕션에서 사용 확인.

### 6.5 imapclient 유지보수 상태 — **확인됨, 양호하나 단독 유지보수자 리스크**
- `imapclient` 최신 **4.0.1, 2026-09-11 릴리스** — 최근 활동 있음. 다만 "1명의 오픈소스 메인테이너"로 표시됨(버스 팩터 낮음) — 설계서가 대체 불가능한 핵심 의존성으로 쓰는 만큼, **장기적으로 메인테이너 교체/중단 리스크를 낮은 확률의 리스크 항목으로만 인지**해 두면 충분(현재 당장 조치 불필요).
